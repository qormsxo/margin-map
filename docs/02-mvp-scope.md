## 1. MVP 정의

**MVP**는 단일 매장 운영자가 메뉴 이론 원가·공헌이익을 계산하고, 차별화 1순위(A·B·E)로 “무엇이 나빠졌는지”를 실데이터 기반으로만 확인할 수 있는 최소 제품이다.

- 계정 1개 = 매장 1개
- 다매장 전환 UI 없음
- 데이터 모델은 Organization → Store로 확장 가능하게 설계

---

## 2. MVP에 포함

### 2.1 계정·매장

- 이메일 기반 인증 (단일 사용자 / 단일 매장)
- 가입 시 Organization 1 + Store 1 자동 생성
- Store 스코프로 모든 업무 데이터 격리

### 2.2 핵심 원가

- 식재료 CRUD (단위, 구매 규격·가격, 면/과세, 단위원가)
- 프렙(PrepRecipe) CRUD (산출량 yieldQty, 중첩 레시피). **수율(손질 손실률) 필드 없음**
- 메뉴·레시피 라인 CRUD
- 판매 채널 (수수료율, 결제 수수료, 배달비)
- 이론 원가·공헌이익·공헌이익률 계산 ([07-formulas.md](07-formulas.md))
- 메뉴별 원가·수익성 대시보드
- 기본 시뮬레이션 (판매가 / 재료가 / 수수료 what-if). 기본은 비영속

### 2.3 차별화 1순위

| 코드 | 포함 범위 |
|------|-----------|
| DF-A | 기간별 실제 사용량 또는 실제 사용 원가 **수동 입력**, 이론 대비 차이액·차이율·추이. 실데이터 없으면 빈 상태 |
| DF-B | 식재료 단가 변경 시 이력 append, 영향 메뉴, 원가·공헌이익 전후 비교 |
| DF-E | 주간 스냅샷 비교 + 규칙 기반 알림. 최소 데이터(연속 주) 미달 시 **결과 미생성** |

### 2.4 플랫폼

- Next.js 반응형 웹
- PWA: Web App Manifest, 아이콘, Service Worker (앱 셸 / 네트워크 우선)
- Docker Compose PostgreSQL
- `/api/v1` + Zod + `domain/` 순수 로직

## 3. MVP에서 제외

### 3.1 명시적 제외 (승인 없이 추가 금지)

1. 식재료 손질 **수율** 계산
2. **조리시간** 및 **인건비** 분석

### 3.2 초기 범위 제외

| 항목 | 비고 |
|------|------|
| 다매장 UI·매장 전환 | 스키마만 확장 가능 |
| POS 연동 | 판매·사용 자동 수집 없음 |
| iOS | 제외 |
| 네이티브 Android | TWA 패키징만 검토. 네이티브는 요구 확인 후 |
| AI 영수증 OCR | 핵심 안정화 후 입력 보조만 |
| 결제·구독 빌링 | 후순위 |
| 완전한 오프라인 동기화 | PWA는 셸 수준 |
| 재고 발주·구매 발주 시스템 | 범위 밖 |
| 손익계산서 전체 (임차료 등 고정비) | 범위 밖 |

### 3.3 차별화 2순위의 MVP 경계

| 코드 | MVP | 이후 |
|------|-----|------|
| DF-C | 판매량 **수동 입력**은 Phase 1 말~Phase 2에서 착수 가능 | CSV 가져오기·자동화 |
| DF-D | **기본** 시뮬레이션은 MVP 포함 | 다채널 동시 비교, 목표 공헌이익률, 다시나리오 저장 고도화 |

## 4. 페이즈 경계

상세 일정·완료 기준은 [10-implementation-plan.md](10-implementation-plan.md)를 따른다.

| Phase | 범위 |
|-------|------|
| 0 Scaffold | Next.js, Prisma, Docker, 인증, Store 부트스트랩 |
| 1 Core | 재료·프렙·메뉴·채널·대시보드·기본 시뮬 |
| 2 Diff-1 | B 가격 이력·영향, A 실제사용·차이, E 주간 규칙 |
| 3 PWA | 설치 가능성 검증 |
| 4 Diff-2 | C 판매량 통합, D 시뮬 고도화 |
| 5 Android | Bubblewrap TWA, Play 테스트 트랙 |
| 6 Optional | AI 입력 보조 (추출 → 사용자 확인 후 저장) |

## 5. 수락 기준 (MVP)

1. 레시피·단가·채널만으로 메뉴 공헌이익이 문서 공식과 일치한다.
2. 재료 단가 변경 시 이력이 남고, 영향 메뉴 전후 비교가 가능하다 (DF-B).
3. 실제 사용 입력이 없으면 DF-A·DF-E가 허위 수치를 만들지 않는다.
4. 수율·인건비 관련 UI·API·DB 필드가 없다.
5. 한 계정에서 매장 1개만 사용 가능하며, 다매장 UI가 없다.
6. HTTPS 배포 환경에서 PWA 설치가 가능하다.
