## 1. 제품 개요

MarginMap은 음식점·카페 운영자가 **메뉴별 수익성**을 계산하고, **원가 변동**과 **수익성 악화**를 추적하는 서비스다.

초기에는 Next.js 기반 반응형 웹과 PWA 설치를 제공하고, 동일 API·도메인 로직을 재사용해 Android(TWA)로 확장한다. iOS는 초기 범위에서 제외한다.

---

## 2. 목표와 비목표

### 2.1 목표

- 레시피·구매 단가·채널 수수료를 반영한 **결정론적** 메뉴 원가·공헌이익 산출
- 재료 가격 변동이 메뉴에 미치는 영향을 이력과 함께 보여 줌
- 이론상 원가와 실제 사용 원가의 차이를 사용자가 입력한 실데이터로만 추적
- 주간 규칙 기반 이상 징후를 대시보드에 표시 (데이터 부족 시 미생성)
- 웹·PWA·Android가 같은 비즈니스 규칙을 사용

### 2.2 비목표 (명시적 제외)

다음 기능은 **구현하지 않는다**. 별도 승인 없이 요구사항·DB·일정에 추가하지 않는다.

1. 식재료 손질 **수율** 계산
2. **조리시간** 및 **인건비** 분석

또한 초기 MVP에서는 POS 자동 연동, 다매장 UI, iOS, 네이티브 Android 앱, AI가 검증 없이 계산·저장하는 흐름을 제공하지 않는다.

## 3. 페르소나

### 3.1 1차 페르소나: 단일 매장 운영자

- 음식점 또는 카페를 혼자 또는 소규모로 운영
- 메뉴 원가를 엑셀·감에 의존하거나 가끔만 계산
- 배달앱·카드 수수료를 빼면 “남는 돈”이 불명확
- 재료값이 올라도 어떤 메뉴부터 손댈지 모름

### 3.2 니즈

- 메뉴당 재료 원가와 공헌이익을 빠르게 확인
- 재료가 변경 시 영향 메뉴를 한눈에 파악
- 이론 사용량과 실제 사용량의 차이로 로스·과다 사용 단서 확보
- 주간 단위로 “이번 주 나빠졌는지”를 규칙으로 알림

## 4. 용어집

문서 전반에서 아래 용어를 통일한다.

| 용어 | 정의 |
|------|------|
| 매장 (Store) | 원가·메뉴 데이터가 귀속되는 운영 단위. MVP는 계정당 1개 |
| 조직 (Organization) | 계정·소유권의 상위 단위. 추후 다매장 확장을 위해 존재 |
| 식재료 (Ingredient) | 구매·재고 단위로 관리하는 원재료 |
| 프렙 / 반제품 (PrepRecipe) | 다른 레시피에 들어가는 중첩 레시피. 산출량(yieldQty)만 둠. 손질 수율 필드 없음 |
| 메뉴 (MenuItem) | 판매 대상. 판매가와 레시피를 가짐 |
| 레시피 라인 (RecipeLine) | 메뉴 또는 프렙에 들어가는 식재료/프렙과 투입량 |
| 단위원가 (unitCost) | 기본 단위당 식재료 원가 |
| 이론상 원가 | 레시피·단가·판매량 기준으로 계산한 예상 식재료 원가/소비량 |
| 실제 원가 | 사용자가 입력한 실제 사용량 또는 실제 사용 원가 |
| 공헌이익 (contribution) | 판매가 − 식재료원가 − 채널·결제·배달 비용 |
| 공헌이익률 (contributionMargin) | 공헌이익 ÷ 판매가 |
| 판매 채널 (SalesChannel) | 홀, 배달앱 등 수수료·배달비가 다른 판매 경로 |
| 차이 (variance) | 실제 − 이론 (수량 또는 금액) |
| 시뮬레이션 | 운영 데이터를 바꾸지 않는 what-if 계산 |

## 5. 기능 요구사항

### 5.1 기본 기능

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-01 | 식재료 정보 관리 (이름, 단위, 구매 규격·가격, 면/과세) | P0 |
| FR-02 | 메뉴 및 레시피 관리 (프렙 중첩 포함) | P0 |
| FR-03 | 재료별 구매 가격과 사용량 기반 이론 원가 계산 | P0 |
| FR-04 | 결제 수수료, 판매 채널 수수료, 배달 비용 계산 | P0 |
| FR-05 | 메뉴당 공헌이익 및 공헌이익률 계산 | P0 |
| FR-06 | 메뉴별 원가 및 수익성 대시보드 | P0 |
| FR-07 | 판매 가격 및 원가 변경 기본 시뮬레이션 (저장과 분리) | P0 |

### 5.2 차별화 기능

우선순위는 차별화 확장 순서다. 기본 원가 계산·기본 시뮬레이션은 핵심 기반으로 먼저 구현한다.

#### 1순위

| ID | 기능 | 요약 |
|----|------|------|
| DF-A | 이론상 원가와 실제 원가의 차이 추적 | 이론 소비량 vs 실제 입력, 차이액·차이율·기간 추이. 실데이터 없으면 미표시 |
| DF-B | 식재료 가격 변동의 메뉴별 영향 분석 | 가격 이력 보존, 영향 메뉴, 원가·공헌이익 전후 비교 |
| DF-E | 주간 원가·수익성 이상 징후 감지 | 규칙 기반. 데이터 부족 시 결과 미생성. AI 비의존 |

#### 2순위

| ID | 기능 | 요약 |
|----|------|------|
| DF-C | 판매량과 공헌이익 통합 분석 | 수동/CSV 판매량 × 단위 공헌이익. 추측 판매량 금지 |
| DF-D | 판매 가격·목표 수익률 시뮬레이션 고도화 | 다채널·목표 공헌이익률·다시나리오. 시뮬레이션과 운영 데이터 분리 |

상세 사용자 흐름: [03-differentiator-flows.md](03-differentiator-flows.md)

### 5.3 AI 사용 원칙

- 핵심 원가·공헌이익·시뮬레이션·이상 징후는 **결정론적 로직**만 사용한다.
- AI는 핵심 기능 안정화 후, 영수증·원가표에서 재료명·수량·단위·가격을 **추출하는 입력 보조**로만 추가할 수 있다.
- AI가 계산 결과를 임의 생성하거나, 사용자 확인 없이 저장하지 않는다.

### 5.4 데이터 정직성

- 실제 소비량·판매량이 없으면 임의 생성·추정 표시를 하지 않는다.
- 분석 결과가 없을 때는 빈 상태와 “필요한 입력”을 안내한다.
- 가격 변경 시 기존 값을 덮어쓰지 않고 이력을 남긴다.

## 7. 성공 지표 (제품)

정량 KPI는 출시 후 계측 설계와 함께 확정한다. 문서 단계의 성공 정의는 다음과 같다.

- 동일 계산이 웹·PWA·(추후) Android API에서 일치

## 8. 가정과 제약

1. MVP는 **계정 1개 = 매장 1개**. 다매장 전환 UI는 없다.
2. POS 연동이 없으므로 판매량·실제 사용량은 수동 입력(이후 CSV)에 의존한다.
3. 프렙은 중첩 레시피와 산출량만 지원하며, 손질 손실률(수율)은 두지 않는다.
4. 경쟁사 기능·가격은 [04-competitive-research.md](04-competitive-research.md)의 확인된 자료만 인용한다.
