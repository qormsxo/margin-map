# Stage 1: 차별화 기능 데이터 수집 가능성 검토

| 항목 | 내용 |
|------|------|
| 전제 | POS 연동 **없음** (MVP·Stage 1) |
| 관련 | [11 데이터](11-stage1-data-design.md), [12 API](12-stage1-api-design.md), [03 흐름](03-differentiator-flows.md) |
| 원칙 | 수집 불가·미입력 시 추정으로 채우지 않음 |

---

## 1. 요약 판정

| 기능 | 필요 데이터 | POS 없이 수집 | Stage 1 입력 방식 | 미입력 시 동작 |
|------|-------------|---------------|-------------------|----------------|
| 기본 이론 원가·공헌이익 | 재료가, 레시피, 채널 수수료, 판매가 | 가능 | 수동 CRUD | 해당 메뉴 원가 미완성 표시 |
| DF-B 가격 영향 | 단가 변경 이력, 레시피 | 가능 | 가격 수정 시 자동 history | 이력 없으면 영향 분석 없음 |
| DF-A 이론 vs 실제 | 기간 판매량 + 실제 사용량/원가 + 레시피 | 가능(수고) | 수동 + CSV | run=`INSUFFICIENT_DATA`, 결과 빈 배열 |
| DF-E 주간 이상 | 연속 2주 스냅샷 가능한 원천 | 부분적 | 주간 run + 사전 입력 | `dataSufficient=false`, 알림 없음 |
| DF-C 판매×공헌 | 기간 메뉴 판매량 | 가능 | 수동 + CSV | 분석 거부/빈 결과 |
| DF-D 시뮬레이션 | 현재 Master만 | 가능 | 오버라이드(비영속) | 해당 없음 |

**결론:** 차별화에 필요한 데이터는 POS 없이도 **수동·CSV로 수집 가능**하다. 다만 A/E/C는 입력 부담이 제품 마찰의이므로 UX·템플릿 CSV가 필수다. 입력이 없으면 기능을 끈 상태로 두는 것이 설계 의도다.

## 2. 데이터 소스별 검토

### 2.1 식재료·구매 가격·이력 (DF-B 기반)

| 항목 | 내용 |
|------|------|
| 원천 | 영수증, 거래명세서, 발주 메모, 기억 |
| 수집 | 앱에서 구매가·규격 입력. 변경 시 history 자동 |
| CSV | `name,base_unit,purchase_qty,purchase_price,tax_type` |
| 리스크 | 단위 환산 실수 → baseUnit 고정 집합 + 미리보기 unitCost |
| 추정 | 금지. 시세 API로 자동 채우지 않음 (후순위·확인 후만) |

### 2.2 메뉴·레시피·프렙

| 항목 | 내용 |
|------|------|
| 원천 | 레시피 노트, 조리 관행 |
| 수집 | 수동 라인 입력 |
| 리스크 | 프렙 누락 → 이론 원가 과소. 실제와 차이(A)로 드러날 수 있음 |
| 수율 | **수집·모델링하지 않음** |

### 2.3 판매 채널 수수료

| 항목 | 내용 |
|------|------|
| 원천 | 배달앱 계약, PG 수수료표 |
| 수집 | 채널별 rate/fixed 수동 |
| 리스크 | 중개+배달 이중 기입 (조건 9) → UI 설명 + 경고 |
| 검증 | 합산식 단일화. 시뮬레이션도 치환만 |

### 2.4 기간별 판매량 (DF-A 이론량, DF-C)

| 항목 | 내용 |
|------|------|
| 원천 | POS 엑셀보내기, 배달앱 정산, 수기 장부 |
| 수집 | 기간 생성 후 메뉴별 qty 수동, 또는 CSV |
| CSV 컬럼 | `menu_id` 또는 `menu_name`, `qty`, optional `channel_name` |
| 금지 | 전주 평균으로 빈 메뉴 채우기, “예상 판매” 저장 |
| 판정 | **수집 가능**. 주 1회 입력 가정 시 A/E/C 동작 |

### 2.5 실제 소비량·실제 원가 (DF-A)

| 항목 | 내용 |
|------|------|
| 원천 | 재고 실사(기초−기말+입고), 사용 일지, 매입 합계(러프) |
| 수집 | 식재료별 `actualQty` 또는 `actualCost` |
| CSV | `ingredient_id|name`, `actual_qty`, `unit`, optional `actual_cost` |
| 난이도 | 판매량보다 높음. MVP는 **주요 식재료만** 입력해도 해당 행만 차이 표시 |
| 금지 | 이론량을 실제란에 복사하는 자동 기능(실수 유도) |
| 판정 | **수집 가능(선택적 완전성)**. 전 재료 필수는 아님 |

### 2.6 주간 이상 징후 (DF-E)

| 항목 | 내용 |
|------|------|
| 필요 | (1) 재료/메뉴 Master (2) 가능하면 주간 판매·실사용 (3) 가격 history (4) 연속 WeeklySnapshot |
| E1·E2 | 스냅샷만으로도 메뉴 이론 원가·공헌이익 WoW 비교 가능 (판매량 없이 Master 스냅샷) |
| E3 | **실제 사용 + 판매량** 필요. 없으면 규칙 스킵 |
| E4 | 해당 주 IngredientPriceHistory만으로 가능 |
| 판정 | E1/E2/E4는 저마찰로 가능. E3는 A 데이터 의존. 데이터 부족 시 알림 미생성 |

**주간 기준 통일:** `weekStart` 월요일, 동일 `channelId`·`basisVersion`, CostBasisSnapshot 동결 ([11](11-stage1-data-design.md)).

### 2.7 시뮬레이션 (DF-D)

추가 외부 데이터 불필요. Master 읽기 + draft 오버라이드.

## 3. CSV 가져오기 명세 (Stage 1 설계)

| Import | 엔드포인트 | 필수 컬럼 | source |
|--------|------------|-----------|--------|
| 판매량 | `POST /sales-periods/:id/import` | menu_id 또는 menu_name, qty | `CSV_IMPORT` |
| 실제 사용 | `POST /actual-usage-periods/:id/import` (12에 대칭 추가 가능) | ingredient_id 또는 name, actual_qty 또는 actual_cost | `CSV_IMPORT` |
| 식재료 초기 | 선택 `POST /ingredients/import` | name, base_unit, purchase_qty, purchase_price | 생성=MANUAL/CSV |

공통:

- UTF-8, 헤더 1행
- 매칭 실패 행은 skip + reason (추정 매핑 금지: 유사도 자동 병합 없음)
- 부분 성공 허용, 성공 건수만 저장

## 4. 최소 입력으로 가치 내는 경로

운영자가 처음 쓰는 권장 순서:

1. 식재료 + 메뉴 레시피 + 채널 → **즉시** 공헌이익 대시보드  
2. 재료가 한 번만 바꿔도 → **DF-B**  
3. 주 1회 판매량 CSV → **DF-C** 시작, A 이론량 가능  
4. 주요 재료 실사용만 입력 → **DF-A**  
5. 매주 `/weekly/run` → **DF-E** (E3는 4번 이후)

이 경로는 POS 없이도 성립한다.

## 5. 수집 불가능·비범위로 남는 것

| 데이터 | 취급 |
|--------|------|
| POS 실시간 판매 | 비범위. 추후 연동 시 SalesLine.source에 `POS_SYNC` 추가 **별도 승인** |
| 손질 수율 | 수집·저장하지 않음 |
| 조리시간·인건비 | 수집·저장하지 않음. 순이익 산출 불가 → 공헌이익만 |
| 자동 시세 | 기본 없음 |

## 6. 리스크와 완화

| 리스크 | 완화 |
|--------|------|
| 판매·실사용 미입력으로 A/E 공허 | 빈 상태 카피, 템플릿 CSV, “이번 주 최소 입력” 체크리스트 |
| 잘못된 단위 | baseUnit enum, import preview |
| 수수료 이중 기입 | 필드 설명, 합산 미리보기 |
| 과거 주가 현재가로 재계산됨 | CostBasisSnapshot 필수 ([11](11-stage1-data-design.md)) |

## 7. Stage 1 설계 결정 사항 (승인 포인트)

1. 판매·실사용은 **MANUAL | CSV_IMPORT**만 인정한다.  
2. 실사용은 전 재료 필수가 아니라 **입력된 재료만** variance에 포함한다.  
3. 주간 E3는 실사용 데이터가 있을 때만 평가한다.  
4. POS/`POS_SYNC`는 이번 설계에 넣지 않는다.  
5. 수율·인건비 관련 수집 필드를 추가하지 않는다.
